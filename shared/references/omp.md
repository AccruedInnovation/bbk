# OMP Adapter Notes

BBK `0.1.0-alpha.17` replaces OMP's assembled system prompt for the visible BBK controller and every canonical BBK agent. The replacement excludes OMP's generic planning, delegation, verification, completion, and anti-ceremony policy, along with compatibility-discovered client instructions. OMP tool schemas and runtime containment still define physical capability; they do not create BBK authority.

Alpha.17 makes product execution the default forward path once the exact WorkUnit and scope, authority/effect fence, workspace/mutation ownership, and required inputs/toolchain/return route are current. Additional planning, design, context packaging, handoff production, review, or verification design requires a named material risk, unresolved proposition, reason current evidence/templates cannot resolve it, and the smallest resolving action. Deterministic PASS receipts remain current until a declared invalidation key changes. Pre-freeze mechanical defects repair within the same semantic run and physical attempt. Structured role returns are preferred over sealed handoff packages when exact durable transport is unnecessary. Broad product validators are relevant-input scoped and final-candidate bounded; routine assurance is INLINE and grouped; Reviewer dispatch requires a named qualitative risk.

Git and mise are the only global repository-substrate prerequisites. The canonical `mise.toml` owns exact `jj` and Beads versions. Normal BBK execution invokes them through `mise exec`; global `jj` or `bd` discovery is not a prerequisite. Explicit executable paths exist only as bounded test/compatibility adapters. The model-routing schema version governs imported routing compatibility; `package_version` is optional provenance and does not invalidate an otherwise valid routing policy.

RC7/RC8 make compact worker dispatch a token-addressed host contract rather than a model-reproduced payload. The integrity digest is computed over the OMP-hook-visible `context` and one `{agent,name,task}` item, excluding the presentation-only `i` field that OMP 16.4.8 removes before the pre-effect hook. `bbk_control_spawn` serializes the complete preparation transaction, projects the initial Beads assignment internally, and returns one dispatch reference. The reference moves through READY, LEASED, ACTIVATED, and TERMINAL states; failed native launches release the same token for retry, while a changed idempotency key cannot create a second binding for the same logical attempt. On launch uncertainty the controller queries `bbk_control_dispatch_status`; eval, shell, Python, JavaScript, and equivalent dispatch emulation are blocked before effect.

RC8 also canonicalizes jj changed paths to validated repository POSIX form before scope and integration comparisons, excludes the governance-bearing root workspace from source snapshot refresh, and derives integration-request Beads revisions internally. A specific poll denied before effect remains an efficiency finding rather than an executed observation; unblocked polling still fails admission.

RC9 closes the terminal-contract boundary. Every governed child `yield` is checked before OMP accepts it: the declared role-return document must satisfy its exact recursive Draft 2020-12 schema and must match the active immutable binding for role, invocation mode, subject, attempt, session, parent, authority, and effect fence. `bbk_return_template` exposes the bound contract and allowed values; `bbk_return_prepare` constructs, validates, and stores an immutable return and supplies the complete immutable `yield_input`. The hook revalidates that exact full document against the binding-owned prepared record before acceptance. Unprepared or reconstructed full documents are blocked at the governed OMP producer boundary even when independently schema-valid; existing role-return records remain consume-compatible outside that boundary. Focused JSON-pointer diagnostics permit same-attempt mechanical repair; malformed or misbound returns never reach the parent as accepted results.

The visible OMP peer whose kind is `main`, normally `Main`, is the harness-root controller and the only BBK identity that may hold terminal focus or interact with the user. Every named canonical BBK role is a child, including `bbk_root_wayfinder`, `bbk_root_orchestrator`, `bbk_reviewer`, and `bbk_validator_orchestrator`. Main selects one appropriate canonical root, invokes it with OMP `task`, supervises it, and relays human decisions without performing or abbreviating the child's substantive role. With OMP's batch task schema, even one child is dispatched as `{ context, tasks: [{ name, agent, task, ... }] }`: `agent` is the exact canonical role, `name` is a stable IRC/job identifier, and `task` is the complete assignment. Flat-schema hosts use their advertised form and durable `local://` context for reusable background.

In persistent `/bbk` mode, `before_agent_start` returns one `<bbk-controller-system>` block. It contains a compact runtime contract and the complete `bbk` and `bbk-context-routing` procedures, so Main does not spend a skill-read call and does not depend on OMP autoload behavior. `/bbk:exit` restores ordinary OMP prompt behavior for later Main turns. Each generated OMP agent carries a deterministic `<bbk-agent-system role="...">` block containing its complete role contract and mandatory procedures. The extension locates only OMP's marker-bearing child wrapper, verifies the role block against the installed canonical projection, parses only explicit invocation context, and emits one `<bbk-agent-replacement>` system prompt. It fails closed on unknown, stale, malformed, or inconsistent role/procedure material.

Provider-prompt integrity is enforced at `before_provider_request`. The session-bound canonical prompt is checked through supported provider adapters for direct message arrays, OpenAI/DeepSeek messages, OpenAI Responses, Anthropic, Google, generic `systemPrompt`, and one nested request/body/payload wrapper. Exact payloads are `VERIFIED`; recognized contamination is removed and the canonical prompt reinserted as `REPAIRED`; missing bindings, unsupported shapes, and failed repairs are `BLOCKED`. A blocked request uses the host abort control where available and substitutes a sentinel containing no original user content. Non-BBK OMP requests pass unchanged. Each request receives a digest-only `bbk.effective-prompt-receipt.v2`; raw prompts and provider payloads are not persisted. `/bbk:prompt-status` exposes verified, repaired, blocked, and unresolved counts. The guarantee ends at BBK's hook because OMP executes handlers in extension load order and exposes no post-chain finalizer.

OMP child communication uses `hub`/IRC. A canonical child discovers the live peer whose kind is `main`, sends concise `BBK_USER_REQUEST` packets to Main, notifies its semantic parent when required, and uses `replyTo` to preserve request identity. Main asks the smallest material question and returns the answer to the exact waiting peer. Delivery receipts, silence, timeouts, and missing heartbeats are not user responses or proof of failure. Large or authority-bearing material remains in durable governed files with exact identities. Child completion should be event-driven where the host supports it; otherwise BBK uses bounded long waits and backoff rather than repeated roster/list polling.

`/bbk:timing` separates explicit user wait observed while OMP's native `ask` tool is open from total session elapsed. It reports provider, tool, and sub-agent intervals, overlap-aware wall coverage, and unattributed time. `/bbk:agents` carries the same current timing state and identifies `WAITING_ON_USER` campaigns without treating elapsed-minus-user-wait as model compute.

The local artifact-finalization consistency guard remains active. When the user explicitly requires `bbk artifact finalize`, a handoff, passing tests, raw directory, or `artifact seal` is not a substitute. Successful one-shot software finalization binds its external publication receipt and exact source snapshot. Before a completion-bearing relay, OMP runs artifact freshness; any added, removed, changed, or missing selected source blocks the completion claim until local checks and successor finalization are complete. The guard proves local byte consistency only and does not infer semantic review, acceptance, deployment, or release authority.

OMP agent frontmatter intentionally has no `autoloadSkills`. Mandatory procedures are already present in the effective system prompt. Optional BBK procedures and language/domain profiles remain available on demand and are loaded only when material to the assigned responsibility. The prompt compiler records required and standalone module dependencies, emits each shared module once per effective invocation surface, and fails generation on missing or duplicate dependency closure.
