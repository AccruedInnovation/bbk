# OMP Adapter Notes

BBK alpha.12 fully replaces OMP's assembled system prompt for both the visible BBK controller and every canonical BBK agent. The replacement deliberately excludes OMP's generic planning, delegation, verification, completion, and anti-ceremony policy as well as compatibility-discovered `.codex`, `.claude`, `.gemini`, and other client-specific instructions. OMP tool schemas and runtime containment still define physical capability; they do not create BBK authority.

The visible OMP peer whose kind is `main`, normally `Main`, is the harness-root controller and the only BBK identity that may hold terminal focus or interact with the user. Every named canonical BBK role is a child, including `bbk_root_wayfinder`, `bbk_root_orchestrator`, `bbk_reviewer`, and `bbk_validator_orchestrator`. Main selects one appropriate canonical root, invokes it with OMP `task`, supervises it, and relays human decisions without performing or abbreviating the child's substantive role. With OMP's batch task schema, even one child is dispatched as `{ context, tasks: [{ name, agent, task, ... }] }`: `agent` is the exact canonical role, `name` is a stable IRC/job identifier, and `task` is the complete assignment. Flat-schema hosts use their advertised form and durable `local://` context for reusable background.

In persistent `/bbk` mode, `before_agent_start` returns one `<bbk-controller-system>` block. That block includes a compact runtime contract and the complete `bbk` and `bbk-context-routing` procedure bodies as `<bbk-inlined-skill>` sections, so Main does not spend a skill-read call and does not depend on OMP autoload behavior. `/bbk:exit` restores ordinary OMP prompt behavior for later Main turns.

Every generated OMP agent carries a deterministic `<bbk-agent-system role="...">` block containing its complete role contract and mandatory procedure bodies. OMP places that definition and the current task-call data in a marker-bearing native child wrapper. The extension locates only that wrapper, verifies the embedded role block byte-for-byte against the installed canonical projection, parses only its explicit context, plan, worktree, peer-roster, and yield fields, discards all other inherited prompt blocks and compatibility context, and emits one `<bbk-agent-replacement>` system prompt. It fails closed if the marker, catalogue, role projection, or mandatory procedure set is malformed, unknown, stale, or inconsistent.

OMP child communication uses `hub`/IRC. A canonical child discovers the live peer whose kind is `main`, sends concise `BBK_USER_REQUEST` packets to Main, notifies its semantic parent when required, and uses `replyTo` to preserve request identity. Main asks the user the smallest material question and returns the answer to the exact waiting peer. Delivery receipts, silence, timeouts, or missing heartbeats are not user responses or proof of failure. Large or authority-bearing material remains in durable files with path, byte count, and SHA-256.

OMP agent frontmatter intentionally has no `autoloadSkills`. Mandatory procedures are already present in the system prompt. Optional BBK procedures and language/domain profiles remain available on demand and are loaded only when material to the assigned responsibility.
