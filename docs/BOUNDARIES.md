# Boundaries

BBK is a lightweight planning, execution, evidence, and review harness. It
provides practical procedures, generated host agents, project-local `.bbk/`
records, deterministic manifests, candidate identity, configured gate receipts,
worktree leases, installation manifests, and optional coordination projections.

It does not create authority merely because an agent, model, skill, profile, or
host can perform an action. BBK does not claim official lifecycle, readiness,
completion, qualification, release, or organizational authority for Blueprint,
Tenex, a target project, or any other external system.

Harness permissions remain authoritative. Prompt instructions, skills, profiles,
procedures, context packages, or role co-location cannot broaden runtime
permissions. A BBK candidate, receipt, review, or status record proves only the
exact assertion and subject recorded by that object.

`WORKSPACE_IMPLEMENTATION` and `EXTERNAL_EXECUTION` are separate authority classes. The former permits requested implementation artifacts and local checks inside the exact authorized workspace. The latter is required for effects on real hosts, remote systems, credentials, deployment targets, network/service/firewall state, publication, release, or migration. `PRODUCE_ONLY` grants workspace implementation and withholds external execution.

Completion claims are likewise independent. `PLANNING_COMPLETE`, `IMPLEMENTATION_ARTIFACTS_COMPLETE`, `BYTE_INTEGRITY_VERIFIED`, `SEMANTIC_REVIEW_COMPLETE`, `DEPLOYMENT_AUTHORIZED`, `DEPLOYMENT_PERFORMED`, and `LIVE_ACCEPTANCE_VERIFIED` may be stated only when each exact claim is established.

Configured model and effort values are execution defaults, not capability proofs
or authority grants. Material downgrades, unavailable routes, missing tools, and
host limitations must be surfaced rather than silently represented as equivalent.


## Contract implementation status

Alpha.13 distinguishes implemented deterministic capabilities, bootstrap implementations, schema-defined companions, optional host-provided primitives, target-only concepts, and retired-not-implemented concepts. A schema-defined companion such as `TerritoryExecutionBoundary` establishes exact structure and ownership but does not claim a dedicated commit primitive or lease-backed mutation fence exists. Optional host capabilities and model routes must be qualified at invocation time.

## Logical and physical roles

A BBK role is a logical responsibility, not proof that a separate model, process,
or session executed. Compatible logical roles may share one physical invocation
when no authority, return, exposure, or independence boundary is lost. Physical
separation remains mandatory when the required property is independent review,
non-self-approval, worker/integrator separation, or uncontaminated evidence.

## Context

A context package records what was supplied, omitted, redacted, summarized, or
made retrievable, plus effective instructions, tools, capabilities, authority,
effects, freshness, and return requirements. Ambient conversation history is not
authoritative merely because it is visible to a model.

## Evidence exposure and review

Evidence exposure is append-only. Exploratory or previously observed outcomes
can support learning and planning, but criteria selected after exposure cannot be
represented as independent confirmation against that same evidence.

A formal model is a design or evidence artifact, not runtime authority. A receipt
records an operation or observation, not an assertion pass by itself. A review
manifest is a plan, not a result. Learning candidates are proposed-only and do
not rewrite BBK methods or profiles automatically.

## Host execution and transport

BBK cannot enlarge an undocumented host timeout, patch/result bridge size,
tool-output limit, destructive-operation policy, model quota, or provider
capability. Extended worker windows are logical orchestration policy: continue
past preflight, checkpoint before likely interruption, persist an exact handoff,
and resume the same work unit when possible.

Model messages are not authoritative carriers for exact large artifacts. Use
authorized workspace files bound by byte count and SHA-256, with compact model
or Beads pointers. Truncated output is an infrastructure event, not evidence that
the referenced candidate or handoff is invalid.

## Language profiles and Beads

A language or domain profile adds procedures, mappings, and evidence adapters. It
does not broaden scope, grant effects, waive assurance, or create a pass.

Beads may index a compact handoff pointer. The `.bbk` handoff and its referenced
files remain authoritative. A successful Beads update does not accept a decision,
close a finding, prove validation, establish completion, or authorize release.
