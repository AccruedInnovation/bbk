# Alpha.17 critical-path execution and verification economy

BBK Alpha.17 makes product execution the default forward path after an executable WorkUnit is admitted. Alpha.17.0.1 retains these floors and promotes the post-finalization rolling-wave, standing-delivery-authority, active-child effect-ownership, and host-neutral prompt-compilation corrections described in [Alpha.17.0.1 delivery-first execution and prompt compilation](PROMPT-COMPILATION-ALPHA17.0.1.md).

This document describes the canonical Alpha.17 behavior. It supersedes temporary user-scope prompt overlays; generated roles and skills are compiled from the primary specifications in this package.

## Governing execution rules

Alpha.17 applies eight rules across prompt contracts, schemas, deterministic helpers, generated projections, and tests:

1. A deterministic proposition is checked once for an unchanged subject and invalidation-key set. A current PASS receipt must be reused.
2. Worker execution begins when exactly four blocking facts are present: exact work/scope/return route; authority/effect fence; workspace/mutation ownership; and required inputs/toolchain/output carrier/completion checks.
3. A reversible pre-freeze mechanical defect is repaired in the same semantic run and physical attempt. Only the affected gate is rerun.
4. Structured role returns are the default. A sealed handoff package is created only when durable exact transport is materially required.
5. Targeted checks run during implementation. Each applicable broad product validator runs at most once against the final frozen candidate and only when an inspected input changed.
6. Routine assurance defaults to INLINE. Compatible assertions are grouped. Reviewer dispatch requires a named qualitative or cross-cutting product risk that deterministic checks cannot establish.
7. Planning and design stop when executable work, authority, ownership, inputs, and completion checks exist.
8. An effort-only routing change inside a qualified provider/model family is runtime cost tuning, not semantic invalidation.

A support role requested after work is executable must name the material product, authority, safety, interface, environment, or completion risk; the unresolved proposition; why current evidence or a standard template cannot resolve it; and the smallest bounded action that will resolve it. Otherwise the caller proceeds with execution or returns `NO_MATERIAL_SUPPORT_WORK`.

## Retained governance floors

The optimization target is minimum repeated process consistent with the following non-negotiable floors:

- exact WorkUnit identity and bounded scope;
- explicit write and effect authority;
- one mutation owner or positive serialization for every mutable surface;
- no unauthorized external, destructive, irreversible, privileged, or secret-bearing effects;
- fixed interfaces, protected floors, and accepted semantic decisions;
- immutable candidate identity after freeze;
- applicable product checks before completion or readiness claims;
- preservation of genuine failures, findings, cleanup, residuals, blockers, and continuation state;
- no conversion of an unproved proposition into PASS or completion;
- no child self-acceptance, self-release, or substitution for user authority.

## Canonical prompt compilation

The primary policy is `bbk-prompt-critical-path-execution` in `spec/prompt-modules/`. All 19 canonical roles include it. Related product-first, handoff, mechanical-admission, evidence-receipt, assurance, candidate-review, and liveness modules contain compatible subordinate rules.

`spec/method-content.json` now declares a module dependency policy for every skill:

```json
{
  "requires_prompt_modules": ["module-already-guaranteed-by-every-loading-role"],
  "standalone_prompt_modules": ["module-that-must-remain-expanded-in-the-installed-skill"]
```

The compiler validates the exact dependency closure and catalog order. Required modules become compact references in generated `SKILL.md` files; standalone modules are expanded exactly once. Generation fails for missing, overlapping, unknown, misordered, or incomplete dependencies. Generated frontmatter records both dependency sets.

## Verification receipts and reuse

`tools/verification_economy.py` implements the Alpha.17 record semantics and provides a JSON CLI plus Python API. The primary schema is `bbk.verification-receipt.v1`.

A verification identity binds:

- claim ID;
- exact subject identity and revisions/digests;
- method, method version, tool identity, and procedure identity;
- configuration, environment, profile, and workspace/host context where applicable;
- explicit invalidation keys;
- result and evidence references;
- producer role, semantic run, and physical attempt;
- receipt integrity digest.

Before a deterministic check, `pre_check` derives the verification key and queries current receipts. An unchanged PASS returns `REUSED_RECEIPT` with `execution_authorized: false`. Execution is authorized only when no current PASS exists or the contract explicitly requires an independent method. Independent judgment alone does not authorize duplicate mechanics.

The package includes:

```text
spec/schemas/bbk-verification-receipt-v1.schema.json
spec/schemas/bbk-verification-budget-v1.schema.json
spec/schemas/bbk-admission-certificate-v1.schema.json
```

Legacy receipts without invalidation keys remain readable, but reuse requires a conservative adapter that can bind the known subject, tool, configuration, and environment. Alpha.17 does not silently reinterpret a legacy PASS as a current invalidation-aware receipt.

## Four-fact dispatch admission

The deterministic dispatch helper requires exactly these facts:

1. `work_scope_return` — exact WorkUnit/subject, bounded scope, and parent return route;
2. `authority_effect_fence` — current authority and effect fence for the next action class;
3. `workspace_mutation_ownership` — workspace and mutation owner or positive serialization;
4. `inputs_toolchain_carrier_checks` — required inputs, selected profile/toolchain, output carrier, and completion checks.

All four facts produce a reusable boundary admission certificate. Omitting one produces only that typed blocker. Current campaign, profile, package, or environment receipts are consumed by reference and are not reconstructed merely because work crossed a role or process boundary.

## Mechanical repair and candidate transitions

Alpha.17 classifies encoding, BOM, line-ending, terminal-newline, canonicalization, serialization, schema-shape, controlled-vocabulary, generated-metadata, path-normalization, digest, byte-count, manifest, package, carrier, locator, unambiguous ledger/checkpoint formatting, and deterministic profile/tool projection defects as mechanical unless they alter semantics or authority.

Before freeze or an irreversible/external effect, the system preserves the failed materialization and failure receipt, regenerates only the affected artifact or receipt, reruns only the failed mechanical gate, and continues in the same semantic run and physical attempt. A mechanical defect does not create a successor plan, architecture/review cycle, WorkUnit, authority package, campaign, or zero-credit lineage.

After freeze, a product-byte change creates a successor candidate and the smallest affected recheck set. Successor planning is permitted only when a semantic assumption, interface, authority condition, protected floor, ownership rule, safety/security property, or completion meaning changed.

Canonical artifact classes declare encoding, BOM, line-ending, terminal-newline, serialization, and governing identity policy. Where both forms matter, records may carry `canonical_content_digest` and `raw_byte_digest`; raw identity remains decisive for frozen executables and exact reproduction artifacts.

## Validator and assurance economy

Broad validators declare inspected paths/input selectors, implementation and configuration inputs, focused-check mapping, receipt identity, and final-candidate requirements. `.bbk/**`, planning, handoff, evidence, log, or coordination-only changes do not trigger product validators that do not inspect those surfaces.

A relevant product change permits targeted checks during work and at most one applicable broad final pass against the frozen candidate. Changing validator code or configuration invalidates its receipt. Revalidation after repair is limited to failed assertions, direct impact closure, and explicit invalidations.

Compatible assertions sharing candidate, method/toolchain, environment, fixtures, exposure, and independence requirements are grouped into one Validator assignment and evidence operation. Routine work uses at most one bounded independent final pass. Reviewer dispatch is denied unless a named qualitative or cross-cutting product risk remains after deterministic evidence is considered.

## Metrics and replay fixtures

`tools/verification_metrics.py` extracts process and quality metrics from `bbk.verification-economy-event-log.v1` records and validates routine budgets. It reports:

- time to first outcome-bearing Worker action;
- planning/coordination/assurance sessions per Worker session;
- receipt reuse and avoided-check counts;
- handoff verification by unchanged subject;
- validator invocations and relevant-input status;
- attempt churn by cause and in-place mechanical repairs;
- reviewer and support-role fan-out;
- child polling/list calls;
- product defects, escaped defects, and preserved failed assertions;
- effective prompt bytes/tokens and compaction counts.

The compact replay fixtures are:

```text
fixtures/verification-economy/excessive-verification-alpha16-codex.json
fixtures/verification-economy/alpha17-compliant-replay.json
```

The baseline fixture preserves the reported 79 sessions, 7,562 shell calls, 470 handoff-verification commands, 33 repository-validator invocations, 30 planning/design validator invocations, four Worker sessions, and four observed attempt-churn causes without expanding thousands of individual events. The compliant replay must pass every routine budget.

Run the extractor with:

```bash
python tools/verification_metrics.py \
  fixtures/verification-economy/alpha17-compliant-replay.json \
  --fail-on-budget
```

## `mise`, `jj`, Git, and Beads

The package-root `mise.toml` is the canonical versioned substrate definition:

```toml
[tools]
"github:gastownhall/beads" = "1.1.0"
jj = "0.43.0"
```

Users need Git and mise globally. They do not need global `jj` or `bd` installations. BBK derives version-bound commands from the effective project/package tool table:

```text
mise exec jj@0.43.0 -- jj ...
mise exec github:gastownhall/beads@1.1.0 -- bd ...
```

`tools/substrate/mise_adapter.py` owns declaration lookup and launcher qualification. `jj_adapter.py`, `beads_adapter.py`, the substrate doctor, legacy `bbk beads` commands, and the automated qualification campaign use the same path. A project-local tool declaration may deliberately override the package default; its configuration digest invalidates affected receipts. Explicit direct executable paths remain available only for controlled offline tests and compatibility adapters.

Git remains a direct global prerequisite. `jj` change/commit identity and canonical tree digests anchor candidates where appropriate. Beads is a lifecycle/index projection and references authoritative `.bbk` artifacts rather than replacing them.

## Model routing

`spec/model-routing.json` is the canonical 19-role default supplied with this package. `schema_version` governs routing compatibility. `package_version` is optional provenance: it may be absent or differ from the installed BBK label without invalidating an otherwise conforming v1/v2 policy.

Routing validation still requires exact live-role coverage, required host objects and fields, valid profile references for legacy v1, and non-empty model/effort values. Effort-only changes within an already qualified provider/model family do not invalidate product semantics or deterministic evidence.

## Alpha.17.1 and Alpha.18 boundary

Alpha.17 includes the canonical behavior, record schemas, receipt index semantics, dispatch/repair/validator/assurance helpers, prompt compilation, replay fixtures, metrics, and deterministic tests needed to remove the observed critical-path failure mode.

Alpha.17.1 may harden automatic host enforcement with:

- a universal pre-effect duplicate-check gate;
- a richer invalidation-key dependency engine;
- automatic campaign/boundary/candidate certificate issuance;
- stricter mechanical-versus-semantic transition classification;
- richer receipt-index querying and reuse telemetry;
- stronger denial of improper successor transitions.

These deferrals do not preserve the Alpha.16 failure mode: Alpha.17 already makes reuse mandatory in canonical contracts, scopes broad validators, permits same-attempt mechanical repair, stops planning when work is executable, compiles duplicate modules out of generated skills, and tests those semantics deterministically.

Alpha.17 final retains OMP event-delivered child results, blocking cross-channel waits, and a deterministic five-minute nonblocking-probe floor. Alpha.18 may add richer host-native wake/timer telemetry, adaptive assurance budgets, fully minimal per-invocation prompt packages, deeper `jj`/Beads/mise visualization, and cross-run learning from verification economics. Those optimizations must not weaken evidence truth or the retained governance floors.

## Manual provider qualification

The approved RC9 Windows/provider campaign established the Alpha.17 final OMP 16.4.8 gate. The retained companion kit remains available for post-release regression and must capture role/session counts, time to Worker execution, handoff verification by digest, validator input relevance, receipt reuse, attempt churn, support-role fan-out, final product checks, findings, and provider cost/tokens where available. Credentialed Codex/Pi parity and OMP 17.2.9 remain unclaimed.

A PASS must bind the exact RC archive digest, retain authority/effect/ownership controls, satisfy the same or stronger product acceptance criteria, and preserve failed assertions or residual risks. Any product change after the candidate digest is established requires a successor RC and a new manual result.
