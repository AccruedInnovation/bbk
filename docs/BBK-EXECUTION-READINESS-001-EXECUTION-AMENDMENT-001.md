# BBK Execution Readiness — Execution Amendment 001

Decision ID: `DEC-ER-017`  
Effective: 2026-08-17  
Authority: controlling user authorization to make broad execution-process changes  
Scope: campaign `BBK-EXECUTION-READINESS-001`, M2 through M6  
Status: accepted and immediately effective

## Why this amendment exists

M2 delivered useful product corrections, but the execution process repeatedly converted deterministic setup and evidence-carrier faults into new Root Wayfinder baselines, Territory boundaries, Reviewer attempts, candidate ceremonies, and handoffs. By r12 the campaign had accumulated twelve accepted baseline revisions while still attempting the first user installation.

The churn was not evidence that the semantic objective was unstable. The repeated causes were mostly execution substrate and carrier issues: missing child-dispatch exposure, path and schema shape mistakes, package-selection scope, launch environment and namespace binding, return identity publication, ad hoc PowerShell capture, and workspace-wide source-sanity scope. The campaign also proved several real product defects and fixed them: install traversal of governance trees, release selection of `.bbk/.beads/.jj`, strict package selection parity, Terra routing, and mandatory mise-managed Beads.

The process therefore changes without weakening the product outcome, milestone order, protected history, non-averaging assertions, or final independent assurance.

## Immediate milestone disposition

M1 remains complete.

M2 is complete when this amendment is durably recorded because its substantive repository outcome is already established:

- exactly the three child-spawning Luna roles route to Terra with reasoning and spawn edges unchanged;
- mandatory Beads policy, checked-in CLI ownership, mise-managed invocation, and generated projections are implemented and focused-tested;
- candidate r3 is sealed and grouped assurance passed `ER-M2-001`, `ER-M2-002_PREINSTALL_DEPENDENCIES`, and `ER-M2-003`;
- package selection and strict verification pass for the selected candidate;
- the user installation remains unchanged at the last reconciled `3699/0/0` state.

The official user update is moved from M2 to M6. Installing M2 bytes immediately before M3–M5 change the same installed surfaces is redundant and creates avoidable risk and rework. M6 performs one official updater against the final assured candidate, followed by installed parity and rollback verification.

The r12 diagnostic result is retained as useful evidence: candidate/package source sanity passes while the workspace-wide scan fails on workspace-only evidence/control files. This is a verifier-scope finding for M3's deterministic-operation work, not an M2 completion blocker. The separately planned capture-deviation Reviewer is cancelled as unnecessary; its immutable predecessor evidence remains available to M3 test fixtures.

## Campaign execution envelope

The user's existing authority is consolidated into one envelope through M6:

- repository implementation, tests, deterministic validation, local candidate/package/handoff production, mandatory Beads projection, and one final user-scoped updater are authorized;
- remote publication, deployment, credentials, services, accounts, M7, and M8 remain prohibited;
- root-direct dispatch to canonical leaf Workers and Validators is the standard topology for this campaign because nested orchestration roles repeatedly lacked child collaboration tools;
- this envelope expires at `STOP_M6_COMPLETE`.

No new Root Wayfinder baseline or Territory boundary is required for a physical retry, local mechanical repair, method qualification, carrier repair, evidence completion, deterministic tool addition, or targeted revalidation inside this envelope. A new planning branch is required only if the actor-visible outcome, protected floor, external effect class, or semantic identity meaning changes.

## Streamlined failure routing

Every non-success still gets a compact immutable incident entry, but a Reviewer is not the default.

| Failure class | Default action |
|---|---|
| method, environment, path, namespace, schema, serialization, finalization, carrier, locator, projection, launch, or deterministic tool failure with reconciled effects | repair within the same semantic WorkUnit; rerun only the invalidated method; append incident; no Reviewer or replanning |
| product or package byte defect with exact failing subject | repair by the current milestone owner; create one product successor; run direct-impact gates |
| wrong subject with possible effect, contradictory acceptance evidence, integrity/unowned write, ambiguous external effect, or cross-boundary authority conflict | stop the affected frontier and commission one bounded Reviewer if deterministic reconciliation cannot resolve it |
| repeated identical mechanical fingerprint | reuse prior classification and repair route; recurrence alone does not require review or a new baseline |

The controller may make and record routine dispositions. A Reviewer diagnoses genuinely qualitative ambiguity; it is not a receipt formatter, schema debugger, recovery planner, or permission relay.

## Deterministic tool and evidence rules

1. Use checked-in qualified operations and argv arrays. Do not generate attempt-local PowerShell/Python wrappers.
2. If a necessary deterministic operation is missing, implement one reusable checked-in helper in the current WorkUnit and self-test it before use. Do not create a separate planning phase for the helper.
3. Prequalify each execution harness once per material method/environment revision and reuse the receipt.
4. A deterministic finalizer may repair or republish a carrier without re-executing the underlying Worker or Validator method.
5. Candidate invalidation follows product bytes and declared selection policy. Planning, Beads, carrier, evidence, and attempt changes do not create product successors.
6. Snapshot only the exact selected subject. Whole-workspace copies are prohibited when a tracked manifest, candidate package, or path-set digest proves the same fact.
7. Beads is mandatory for project, phase, WorkUnit, and governing decision objects. Physical attempts and mechanical incidents reuse the WorkUnit bead and are not projected as new semantic objects.

## Remaining execution shape

- M3: one coherent Worker implements diagnostic contracts, deterministic operation registry, verifier-scope correction, directives, projections, and focused tests. Deterministic gates close M3.
- M4: one coherent Worker implements typed identity schema/enforcement and metamorphic tests. Deterministic gates close M4.
- M5: one coherent Worker implements receipt currentness/reuse, recurrence classification, layered stage results, and integration. One grouped independent Validator evaluates the integrated M3–M5 candidate.
- M6: one Worker runs the frozen history/synthetic replay and broad standard/release gates; one grouped independent Validator evaluates the final candidate; one official updater installs the final bytes and proves installed parity; package/handoff/checkpoint finalize and execution stops.

Only directly invalidated tests rerun before M6. Broad standard/release gates run once against the final frozen candidate unless product or method invalidation requires a successor.

## Stop-safe checkpoint rule

Checkpoint at coherent WorkUnit completion, immediately before and after the final user installation, on an unresolved external-effect ambiguity, and at milestone completion. Mechanical incidents append to one milestone ledger. Each checkpoint contains the exact resume action and no synthesis or cleanup agent is required.

## Claim limits

This amendment changes execution method and M2/M6 installation timing. It does not waive a product assertion, mark M3–M6 complete, accept a candidate, authorize publication or deployment, or alter the M6 stop condition.
